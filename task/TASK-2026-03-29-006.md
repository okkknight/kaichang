# TASK.md

## 本轮目标
本轮只完成：让 `progressive` 生成链路里“已经发到前端的候选”也能同步落库，保证前端已经看到的候选在 refine / copy / feedback 时都能查到。

---

## 本轮要做
- 保持 progressive 逐条返回候选的体验不变
- 把候选持久化改成与逐条生成对齐，避免出现“候选已经显示了，但数据库里还没有”的情况
- 确保已成功返回给前端的候选，都能在数据库里找到对应记录
- 如果某一条候选失败，只影响这条候选，不要让已经成功并展示出来的候选丢失

---

## 本轮不要做
- 不要回退到整批最后才一次性返回
- 不要新增重试、规则硬拦截或 slot 级 fallback
- 不要改 refine 链路本身
- 不要改首页交互结构
- 不要顺手扩大到历史记录、点赞点踩、登录等无关功能

---

## 修改范围
允许修改：
- `server/opening/generate-openings.ts`
- `server/db/generation-repo.ts`
- 如确实需要，可少量调整 `app/api/generate-openings/route.ts` 的 progressive 响应语义

不要修改：
- `app/page.tsx`
- `components/*` 中与本问题无关的文件
- `app/api/refine-opening/route.ts`
- `server/opening/prompt-builder.ts`
- `server/opening/opening-quality.ts`
- `prisma/schema.prisma`
- 与本问题无关的 API 路由

---

## 本轮主流程
1. 找到 progressive 链路里候选展示和候选落库的时机差
2. 把持久化调整到与候选逐条产出更一致的时机
3. 确保已经推给前端的候选具备可被 refine / copy / feedback 查询到的数据库记录
4. 保持 progressive 的逐条渲染不变，避免引入新的卡顿或全局阻塞
5. 做最小改动后跑类型检查 / 构建验证
6. 用真实输入手测一次 progressive + refine，确认已展示候选可继续操作

---

## 验收标准
- [ ] progressive 仍然能逐条显示候选
- [ ] 已显示给前端的候选都能在数据库里查到
- [ ] refine 不再因为“候选不存在或已被删除”报错
- [ ] 已成功的候选不会因为后续某条失败而一起丢失
- [ ] `npm run typecheck` 通过
- [ ] `npm run build` 通过

---

- 若遇到未定义需求，默认不实现
- 若发现需要大范围重构，先停止并说明
