# TASK.md

## 本轮目标
本轮只完成：把开头候选生成拆成“单候选独立请求 + 前端逐条渲染”的模式，让用户先看到第一条候选，再继续补齐后续候选，提升首屏体感速度。

---

## 本轮要做
- 把候选生成能力拆成单条候选的独立执行单元，尽量复用现有的分析、策略、prompt、结构化解析、质量校验逻辑
- 让前端不再等待整包 4 条候选全部返回后再渲染，而是按 slot 逐条展示，哪个候选先完成就先显示哪个
- 保持现有的结构化 tool-call / JSON 约束，不要退回自由文本流式输出
- 保留现有的候选去重、质量校验、失败报错逻辑
- 如有必要，补最小化的批次归组字段，确保多条独立请求仍能在历史记录、落库和 UI 中被识别为同一次生成会话
- 保持当前主链路风格不变，用户看到的仍然是候选卡片，不是聊天消息

---

## 本轮不要做
- 不要重做 refine 链路
- 不要把正文改成自由文本流式输出
- 不要新增复杂的任务队列、消息总线或后台 worker 系统
- 不要为了速度牺牲结构化解析和质量校验
- 不要改首页成聊天界面
- 不要顺手扩展到历史记录、点赞点踩、登录等无关功能

## 本轮主流程
1. 找到当前“一次性生成整包候选”的执行点，拆出“单候选生成”能力
2. 保持每条候选仍然走现有的结构化 tool-call / JSON 解析方式，不改成自由文本猜测
3. 在前端把候选卡片改成可逐条追加的状态，第一条完成后先渲染，后续候选继续补齐
4. 让失败只影响对应 slot，不要因为某一条慢或失败就让整批候选一起卡住
5. 保持同一次生成会话的归组能力，必要时补 `batchId` / `slotIndex` 之类的最小字段
6. 做最小改动后跑类型检查 / 构建验证
7. 用真实 provider 的中文输入做一次手测，确认首条候选可以先出现

- [ ] 单个候选请求失败不会阻塞已经成功返回的候选
